## Task 3 — Does `totalStructuralGateRejections` measure the same event in both modes?

**No.** It is an *episode-terminal* counter, and the diagnosis gate's entire purpose is
to keep episodes from reaching that terminal state — so comparing it across
`PivotGatesEnabled` is comparing two different underlying events, not a rate change in
the same event.

Evidence:

- `NexusOrchestrator.cs:241` — `if (result.Outcome == EpisodeOutcome.StructuralGateRejection) totalStructuralGateRejections++;`
  This increments once per **episode**, only when the episode's final outcome equals
  `StructuralGateRejection`. It is not incremented per structural-violation turn.
- `NexusProverSubagent.cs:484` — the actual structural-violation check
  (`SketchValidator.IsStructurallyValid`) runs identically in both modes; this part
  was not touched and is not the source of the discrepancy.
- `NexusProverSubagent.cs:503` — `consecutiveViolations++` also happens identically in
  both modes, on every violation.
- `NexusProverSubagent.cs:512-513` — `else if (consecutiveViolations == 2 && diagnosesThisEpisode < maxDiagnosesPerEpisode && ctx.PivotGatesEnabled)`.
  **This is the branch point.** When `PivotGatesEnabled=false`, this condition is
  always false (short-circuited by `&& ctx.PivotGatesEnabled`), so the 2nd consecutive
  violation always falls through to the `else` at `:578-600`, which immediately
  `return`s `EpisodeOutcome.StructuralGateRejection` — incrementing the orchestrator
  counter.
- `NexusProverSubagent.cs:551-554` — when `PivotGatesEnabled=true` and a diagnosis
  budget remains, the 2nd violation instead triggers a diagnosis call and, on success,
  **resets `consecutiveViolations = 0`** and clears the warning, then `continue`s the
  turn loop. No `EpisodeResult` is returned here — the episode keeps running. The
  `StructuralGateRejection` outcome (and the counter increment) is only reached later,
  at `:578-600`, once `diagnosesThisEpisode >= maxDiagnosesPerEpisode` (default 1) *and*
  a further pair of consecutive violations occurs — or the diagnosis call itself throws
  (`:556-576`, same abort path).

Net effect: with gates off, **any** episode with 2 consecutive violations increments
the counter. With gates on, it takes roughly double the raw violations (one pair
absorbed by the diagnosis, resetting the counter, before the next pair can abort) —
**or the episode may never increment the counter at all**, if the diagnosis genuinely
breaks the cheat pattern and the episode proceeds to `Solved` or `MaxTurnsReached`
without a second pair of violations. There is no other telemetry field that records
raw per-turn structural-violation counts independent of this episode-terminal outcome
(`EpisodeResult` / `ProofResult` in `NexusAgent.Core/Models/ProofResult.cs` has no such
field) — so **any claim that "structural rejects dropped" based on this counter alone
is confounded with the gate's own design**, not independent evidence that the model
cheated less. The A/B below reports it anyway (both raw and per-turn) but does not
treat a drop in it as evidence of anything beyond what the gate is defined to do.

## Task 4 — Diagnosis-loop safety cap

GLM had already added this: `NexusProverSubagent.cs` (pre-existing, `const int
MaxDiagnosesPerEpisode = 1`) caps diagnoses per episode, so the
cheat→diagnose→cheat→diagnose sequence cannot repeat indefinitely — after the cap is
spent, the next 2-violation pair aborts instead of diagnosing again. In practice the
turn loop (`for (int turn = 0; turn < ctx.MaxTurns; turn++)`) already bounds every
episode regardless, so "indefinite" was never literally possible, but the cap makes a
stuck episode terminate promptly instead of burning its full turn budget.

Changes made:
- Promoted the hardcoded `const` to a proper config value, matching the pattern used
  for `MaxTurns`, `FossilMatchThreshold`, etc.: added
  `OrchestratorConfig.MaxDiagnosesPerEpisode` (default `1`, unchanged behavior) in
  `NexusOrchestrator.cs`, threaded through `EpisodeContext.MaxDiagnosesPerEpisode` in
  `NexusProverSubagent.cs`, wired at the `EpisodeContext` construction site in
  `NexusOrchestrator.cs`.
- Added `NexusProverSubagentTests.RunEpisodeAsync_AlwaysStructuralViolation_TerminatesRegardlessOfDiagnosisCap`
  (`NexusAgent.Tests/Agent/NexusProverSubagentTests.cs`), a `[Theory]` over
  `maxDiagnosesPerEpisode ∈ {0, 1, 3}`, driving a mocked LLM that **always** returns a
  renamed/hacked theorem. Asserts the episode terminates via
  `EpisodeOutcome.StructuralGateRejection` well within a generous 50-turn budget (not
  `MaxTurnsReached`), for every cap value — proving termination is a property of the
  cap mechanism itself, not incidental to the default. All 10 tests in that file pass
  (7 original + 3 new theory cases).

### Interpretation

**No independent-solve improvement.** Both arms produced **zero** independent solves
out of 17. Every "solve" in both arms — 5/17 control, 7/17 treatment — is the same
answer-key-citation exploit already documented for this corpus (`exact
<original_declaration>`), not genuine proof search. On the metric the brief designates
as the headline (independent solves, excluding citations), **the pivot gates made no
measurable difference: 0 vs 0.**

**Raw solve count rose (5→7), entirely via more citation exploits**, not via the gates
enabling real proof discovery. This is not evidence the gates help — if anything it's
a reminder that the citation-leak vector (importing `FC100SolvedSet1` puts the
original proof in scope under its original name) is untouched by either arm and
remains the dominant "success" mode on this corpus regardless of gate state.

**Structural rejects (episode-terminal count) dropped 4→1, and per-turn 1.54%→0.38%
(~4x).** Per Task 3, this is exactly what the gate is *designed* to do — it
intercepts the 2nd consecutive violation with a diagnosis call instead of letting it
terminate the episode — so this drop is not independent evidence of "less cheating,"
it's largely the counter measuring a different event, as documented above. It is
reported here for completeness, not as a success metric.

**Diagnoses were cheap and always "succeeded" in the narrow sense of returning a
response (7/7)**, but that did not translate into recovered episodes producing
independent proofs — no episode that hit the diagnosis gate went on to an independent
solve. **Reformulation had a low hit rate**: 10 fired, only 1 produced compiling Lean
(10%), consistent with the known TODO in `NexusOrchestrator.cs:372` that the
reformulation retry loop does not actually feed the compile error back into the retry
prompt (it just resamples the same prompt at temperature — a real gap, out of scope
for this task but worth flagging since it likely caps how effective this half of the
pivot-gates feature can be).

### Caveats on rigor

- **N=17, single run per arm, no repeated seeds.** The sample is small and DeepSeek
  sampling is stochastic; a 5→7 raw-solve swing on 17 problems is well within
  run-to-run noise. Neither this run nor a single repeat could establish statistical
  significance for a solve-count difference this small — and the actual headline
  metric (independent solves) showed no difference at all, so this doesn't change the
  conclusion.
- **Fossil-vault carryover between arms.** Both arms ran against the same live Neo4j
  instance (`neo4j:5-community` — Community Edition has no multi-database support, so
  there was no clean way to give each arm an isolated fossil vault without surgery on
  a shared production-like store, which was avoided as out of scope and risky
  mid-experiment). Checked for contamination directly: both arms retrieved exactly 1
  fossil each (`FossilHits=1`), on the *same* problem (`flt_of_beal_conjecture`), which
  a query confirms predates this A/B (it was already solved in the original 09:27
  baseline run). No evidence either arm benefited from a fossil the *other* arm created
  during this A/B. Given the low retrieval/substitution rate observed (2.9%/3.2% conv
  rate), this was not a material confound for this run, but it is a structural
  limitation of the setup that a future stricter A/B should address (e.g., a
  disposable Neo4j Enterprise instance per arm, or explicit fossil-provenance
  filtering).
- **Citation-leak vector is orthogonal to the pivot gates and dominates the observed
  "solves."** Neither arm's solve count says anything about proof-search capability
  until the import-scope leak (`FC100SolvedSet1` bringing original declarations into
  scope under their original names) is closed — that's a corpus/harness issue, not a
  prover issue, and is out of scope for the pivot-gates question specifically but
  should be flagged before this corpus is used for any future claim about solve rates.

### Bottom line

This is a **negative/null result on the metric that matters**: the pivot gates
(within-episode obstruction diagnosis + between-episode reformulation) produced no
independent solves in either arm, so there is no evidence in this run that they
improve genuine proof-search capability on hard, previously-unsolved problems. They do
measurably change the model's behavior around structural violations (fewer
episode-terminal structural rejects, though that's largely definitional per Task 3;
100% diagnosis "success" rate in the sense of returning usable text; 10% reformulation
compile rate), but none of that behavior change showed up as more real proofs on this
17-problem sample. Given the sample size, this should be read as "no signal of benefit
detected," not "proven no benefit" — but it does not support the claim that structural
rejects dropping constitutes evidence the gates are working, for the reasons in Task 3.
